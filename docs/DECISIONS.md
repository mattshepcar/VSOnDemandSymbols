| D-12 | 2026-11-05 | Reference `Microsoft.VisualStudio.SDK` `17.14.40265` and `Microsoft.VSSDK.BuildTools` `18.9.820` on NuGet. | The template's `18.11.1036`/`18.11.1034` versions are not published on nuget.org. `SDK 17.14.40265` enforces our `[17.14,)` API baseline (NF-8), while `BuildTools 18.9.820` supports SDK-style `<VSSDKBuildToolsAutoSetup>true</VSSDKBuildToolsAutoSetup>` packaging in both VS 2022 and VS 2026. |
| D-13 | 2026-11-05 | Set `IVsDebuggerSymbolSettings170.AutomaticSymbolLoad = false` while on-demand mode is active, and back up / restore it alongside `IsManualLoad`, `IsLoadAdjacent`, and `IncludeList`. | Spike S1 found that VS 17.0+ has an "Automatically include additional symbols when needed" setting (`AutomaticSymbolLoad`, default `true`) under manual-load mode. | D-14 | 2026-11-05 | Use public AD7 + `IVsDebuggerSymbolSettingsManager120A` APIs (no Concord `.vsdconfig` component). | Spikes S1–S5 and S7 confirmed that `SaveSymbolSettings(settings, loadSymbolsNow: false)` updates the engine's include list live during a session, `IDebugModule3.LoadSymbols()` triggers Concord's `OnModuleSymbolsLoaded` to bind pending breakpoints automatically, `IDebugBreakpointErrorEvent2` catches editor-margin breakpoints added mid-session, and `IDebugSymbolSearchEvent2` detects manual loads. |
| D-15 | 2026-11-05 | **Supersedes D-8 and D-14:** Use the **Concord Hybrid** architecture (`SymbolSettingsController` sets manual-load mode flags only, leaving the user's `IncludeList` untouched; an IDE-side Concord component `ConcordSymbolMonitor` handles synchronous module-load symbol loading, on-demand `DkmModuleInstance.TryLoadSymbols()`, symbol-load detection, and breakpoint notifications). | User choice. Concord (`Microsoft.VisualStudio.Debugger.Engine`) is Microsoft's modern, documented debugger extensibility API. Running `IDkmModuleInstanceLoadNotification` in Concord loads symbols synchronously while the debuggee is paused at DLL map time (before `DllMain`/`StartupModule()`), keeps the 800 module-load events off the VS UI thread (NF-1), avoids raw COM `IntPtr` marshaling for breakpoints (`IDkmBreakpointManagerNotification`), and eliminates any need to modify the user's `IncludeList` in VS symbol settings (strengthening Golden Rule #1). |
| D-16 | 2026-11-05 | **Supersedes D-2 and D-11:** Remove the `RecentlyBuilt` trigger (`RecentlyBuiltScanner`, `LoadRecentlyBuilt`, `RecentlyBuiltMaxModules`, `FirstSessionRecentWindowMinutes`, `LastSessionStartUtc`). Symbols are loaded at startup only for modules with breakpoints, modules in the MRU or pinned lists (populated by breakpoints, call-stack/exception breaks, frame activations, or manual loads), and `AlwaysLoadPatterns`. | User decision. Binary modification timestamps are a poor proxy for debugging intent (syncing from source control, switching branches, or editing a shared header rebuilds many DLLs the user isn't actively debugging). Actual debugging intent is already covered by breakpoints, call-stack/exception breaks, manual loads, and the MRU list. |
| D-17 | 2026-11-06 | **Part-supersedes D-15:** Use VS Symbol Settings `IncludeList` for native startup module symbol loading, combined with DTE `Module.LoadSymbols` for mid-session on-demand loading. `DkmModuleInstance.TryLoadSymbols()` throws `NotImplementedException` (`0x80004001` / `E_NOTIMPL`) for native C++ modules in Visual Studio. | Testing against Unreal Engine Lyra in VS 2022 confirmed that Visual Studio's native C++ debug engine (`CppDebug.dll`) does not implement `IDkmSymbolLocator` for native modules. In manual-load mode, VS natively checks `IVsDebuggerSymbolSettings120A.IncludeList` at module map time and loads symbols automatically for matched binary names. The extension manages `IncludeList` dynamically: the user's original `IncludeList` entries are backed up and preserved; wanted module binaries are merged into `IncludeList` before launch and during mid-session triggers; and the `IncludeList` is restored to the user's original entries on session end, solution close, disable, or crash recovery. |
| D-18 | 2026-11-06 | **Amends D-17:** Do **not** reset `IncludeList` at debug-session end. Instead, at session end re-publish the wanted set (now including the session's MRU hits) and write it to `IncludeList`, so it is in place before the next launch whether or not the before-launch hook fires. The user's original `IncludeList` is restored only on solution close, disable, VS exit, or crash recovery (consistent with D-9). Every `IncludeList` write is logged with its reason; a missed before-launch hook logs a warning and applies the list late with `loadSymbolsNow: true`. | Manual testing showed the list being cleared at session end and not in place early enough on the next launch, so breakpoints in `LyraGame` stayed unbound after the editor was fully open. Keeping the list populated between sessions removes the dependency on launch-hook timing. |

| D-19 | 2026-11-06 | **Amends D-15:** The Concord component no longer implements `IDkmBreakpointManagerNotification`. Live-session breakpoint triggers (BP-2) come from a passive AD7 `IDebugEventCallback2` registered with `IVsDebugger.AdviseDebugEventCallback` (`Ad7BreakpointEventListener`). On `IDebugBreakpointErrorEvent2` it schedules one coalesced rescan of `DTE.Debugger.Breakpoints` and queues on-demand loads. | Manual Lyra testing: Concord logged `Breakpoint bound` once the IncludeList loaded `UnrealEditor-LyraGame-Win64-DebugGame.dll`, and the Modules window showed symbols loaded, but the editor glyph stayed hollow ("symbols not loaded") until the breakpoint was removed and re-added. `IDkmBreakpointManagerNotification` is how the AD7 abstraction layer raises `IDebugBreakpointBoundEvent2` to the IDE, so implementing it in our component stopped that update from reaching the UI. The AD7 callback only observes events and is not in that notification path. |
| D-20 | 2026-11-06 | **Supersedes D-1 and D-7; amends D-5, D-16, D-18:** Remove the MRU feature, MRU pruning rules (5 runs / 24 hours), and module pinning. The debugger's `IncludeList` is populated before launch solely for modules with breakpoints (plus `AlwaysLoadPatterns` and preserving the user's original `IncludeList`). During a session, call stack, exception, and frame activation triggers load symbols on demand. No module history is carried across sessions, and no per-solution `state.json` is needed for MRU. | User decision. On-demand symbol loading when execution stops is fast enough that carrying forward previously loaded modules across sessions via an MRU or pinned list adds complexity without meaningful benefit. Removing MRU and pinning eliminates `MruStore`, pruning logic, run counters, MRU eviction, hit recording, per-solution `state.json` persistence, and the need for MRU/pinned management UI in tool windows and context menus. Startup time is maximized because only modules with active breakpoints have symbols loaded at launch. |
| D-21 | 2026-11-06 | **Supersedes D-14, D-15, D-19:** Adopt **V2 Clean-Slate Minimal Architecture** on branch `v2-minimal`. Strip Concord completely (`.vsdconfig`, `vsdconfigtool.exe`, `Microsoft.VisualStudio.Debugger.Engine.dll` unmanaged reference, `ConcordSymbolMonitor`, `ConcordSymbolBridge`, `LoadedModuleRegistry`), strip MSBuild resolution (`MsBuildResolver`, `ProjectModelProvider`, `VCProjectEngine`), and focus solely on Unreal Engine 5.x native C++. | Complete review of Phases 0–4 revealed that Concord provides no functional symbol-loading capability for native C++ in Visual Studio (`DkmModuleInstance.TryLoadSymbols` throws `E_NOTIMPL`), while native `IncludeList` + DTE `Module.LoadSymbols` completely and reliably handles the entire workflow. Stripping Concord and MSBuild reduces the codebase from ~4,200 LOC across 35 files to ~550 LOC across 4 files, eliminates custom build tooling and private IDE DLL dependencies, and removes architectural debt. Documented in `docs/SPEC.md`, `docs/IMPLEMENTATION_PLAN.md`, and `docs/ARCHITECTURE.md`. |
| D-22 | 2026-11-06 | Use wildcard patterns (`UnrealEditor*.exe` and `UnrealEditor-{ModuleName}*.dll`) exclusively in `IncludeList`. | User feedback. Visual Studio's `IncludeList` supports wildcard matching (`*`), so generating explicit configuration-specific names (`-Win64-DebugGame.dll`, `-Win64-Development.dll`, undecorated `.dll`, and `UnrealEditor.exe`/`UnrealEditor-Win64-*.exe`) is redundant. Wildcards match all configurations (Development, DebugGame, Debug, Shipping, hot reload, etc.) with a single clean entry per module and a single entry for the editor executable. |
| D-23 | 2026-11-06 | **Amends D-5:** Remove the `Debug > On-Demand Symbols > Enabled` menu command, sub-menu, and `VSCommandTable.vsct`. | User decision. The toggle provides little to no utility over disabling or uninstalling the extension via Visual Studio's Extension Manager. Removing the menu command eliminates `VSCommandTable.vsct`, simplifies the package lifecycle, and keeps the IDE UI clean and unencumbered. |
| D-24 | 2026-11-06 | Restore AD7 breakpoint bind error observation (`IDebugBreakpointErrorEvent2` via `IVsDebugger.AdviseDebugEventCallback`) in `DebuggerSessionMonitor`. When a breakpoint is added or activated while the debuggee is running (or in break mode), the native debug engine reports a bind failure because the module's PDB is not loaded. `DebuggerSessionMonitor` catches this event, switches to the UI thread, updates `IncludeList` with the candidate binaries, and immediately invokes `mod.LoadSymbols("")` on matching loaded modules in `DTE.Debugger.DebuggedProcesses`, activating the breakpoint mid-session. | Bug fix. In the V2 clean-slate architecture, breakpoint listening was omitted outside F5 launch, leaving breakpoints added or enabled while running unbound and inactive. Re-introducing the passive AD7 callback restores mid-session breakpoint binding without any Concord dependencies. |
| D-25 | 2026-11-06 | Include modules containing disabled breakpoints in `IncludeList` alongside enabled ones. | User decision / bug fix. Visual Studio does not consistently route re-enabling a previously disabled breakpoint through `IDebugBreakpointErrorEvent2` when running. Treating disabled breakpoints identically to enabled ones ensures symbols for their modules are loaded at process startup via `IncludeList`. When the user later enables the breakpoint while running, symbols are already resident in memory and the breakpoint binds immediately without requiring runtime bind error callbacks. |
| D-26 | 2026-11-06 | **Amends D-13, D-17:** Implement scoped symbol server masking during break-mode symbol loading. When execution breaks (or the user changes thread context in the Threads window), remote symbol servers (`UseMSSymbolServers`, `UseNugetSymbolServers`, and remote URLs in `SymbolPaths`) are temporarily masked (disabled) during a local symbol load pass. Visual Studio's native debug engine loads all locally available and cached PDBs for call stacks and threads without querying internet symbol servers. Servers are immediately unmasked upon completion, preserving manual right-click "Load Symbols" from internet servers. Settings backup and crash recovery are extended to cover symbol server flags and paths. | User feedback / bug fix. Breaking into the process left unresolved symbols across the Call Stack and Threads windows. Enabling Visual Studio's `AutomaticSymbolLoad` caused unwanted internet downloads from Microsoft Symbol Servers for OS DLLs. Temporarily masking remote servers allows Visual Studio's native loader to resolve adjacent and local cached PDBs instantly while preventing background network requests, and leaves symbol servers active for manual on-demand loading. |
| D-27 | 2026-11-06 | Call-stack inspection on break walks up to 10 frames per non-current thread, stopping immediately upon encountering the first user-code module. | User decision / bug fix. In large multi-threaded applications like Unreal Engine (120+ background threads), top frames are typically OS synchronization primitives (`ntdll.dll!NtWaitForSingleObject`, `KernelBase.dll!WaitForSingleObjectEx`). Walking call stacks until the first user-code module is encountered (safety-capped at 10 frames) correctly discovers the thread's user-code location (e.g. `UnrealEditor-WebSockets.dll`, `UnrealEditor-HTTP.dll`) so its local symbols load and the Threads window Location column resolves, while avoiding walking the full call stack of every idle background thread. System module symbol load failures are silenced from standard logging to prevent noise. |
| D-28 | 2026-11-06 | Integrate extension settings with Visual Studio's modern Unified Settings framework via `registration.json` and a single top-level category. | User feedback. In modern Visual Studio (VS 2022 17.10+ / VS 2026), legacy `DialogPage` options display a "These settings haven't been migrated yet" banner. Adding `UnifiedSettings/registration.json` via `[ProvideSettingsManifest]`, setting `IsInUnifiedSettings = true` on `[ProvideOptionPage]`, and unifying the category and page names under `"On-Demand Symbols"` (eliminating the redundant `"General"` subpage) migrates the setting into the native Unified Settings experience with full dropdown rendering. |
